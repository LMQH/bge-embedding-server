# ADR-0001：采用 SDD 开发理念

## 状态

已接受，2026-10-21。依据：用户明确指出项目采用 SDD，要求修正相关文档并说明开发理念。按用户要求直接修订 ADR-0001。

## 上下文

项目通过 PRD、ADR、Spec、Plan 分别承载需求、决策、行为与执行信息，需要明确规格如何驱动实现与验收，并统一协作约定、开发流程与模板，确保交付满足已确认的行为契约。

## 决策

采用 SDD（Specification-Driven Development，规格驱动开发）。Spec 是实现、测试与验收的直接依据；PRD 提供需求来源与成功标准，ADR 记录重要决策与约束，Plan 将已确认规格拆成可执行任务并保存真实验证证据。

工作按“需求澄清 → 规格确认 → 实施计划 → 最小实现 → 按规格验证”迭代。行为变更先更新并确认受影响的规格，再实施；实现与规格不一致时先澄清预期行为，不能用现有代码替代需求确认。验收结果关联 Spec 场景或章节，明确通过、失败与未验证项。

仅细化当前需求，不要求一次性完成全部设计。纯文档、Git 等不改变服务行为的任务按任务目标检查，无需新建行为规格。保留 [ADR-0004](0004-minimal-verification.md) 的最小验证范围，不因采用 SDD 增加未请求的测试、工具或自动生成代码流程。

## 替代方案

- 继续只说明文档分类：无法明确规格对实现与验收的约束，容易把文档齐全当成交付完成。
- 先实现再补规格：容易将实现细节反写为需求，失去独立验收依据。

## 后果

- 需求、规格、任务、实现与验证形成可追溯关系；行为变更需要先澄清规格并保持同步。
- 沿用现有目录、编号与工具，不改动服务接口、模型或部署方式；既有未执行验证不因本决策变成通过。
