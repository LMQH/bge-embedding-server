# ADR-0006：进程内结果缓存

## 状态

已接受，2026-10-22。依据：用户指示"不跑本机真实验证，执行修改，然后推到 Mac mini 上去测试"，确认 [PRD-0003](../prd/0003-result-cache.md) 与本决策并要求直接实施。

## 上下文

嵌入推理是纯函数：同一 8bit 模型快照内，相同 token 序列与相同 `return_sparse` 选项的输出确定。重复文本（文档重复入库、热点查询）每次都完整推理，8192 tokens 约 4.8 秒，且服务为单执行位串行（1 执行 + 19 等待），重复请求占用唯一 GPU 位置并推高同队列其他请求延迟。

约束：M4 16GB 统一内存，当前进程 RSS 基线约 630 MiB、Metal 峰值约 977 MiB；[SPEC-0001](../specs/0001-embedding-inference.md) 规定服务不持久化用户文本和返回向量、不引入独立监控系统；项目宪法要求最少代码、不为推测场景增加抽象。tokenize 在请求校验阶段已经完成（`api.parse_body` → tokenize → `check_tokens` → 调度），token 序列先于调度存在。

## 决策

- 进程内内存缓存，随应用 lifespan 创建、随进程退出消失；不落盘、不跨进程、不引入新依赖。进程内存驻留不构成 SPEC-0001 所指的"持久化"。
- 键为 `sha256(token id 序列二进制 + 1 字节 return_sparse 标志)`，按文本条目粒度。token 层建键发生在校验之后：无效输入永不缓存；哈希键不保存原文，规避文本编码 / 规范化歧义。
- 淘汰用 LRU（`OrderedDict`），容量按估算字节预算：dense 固定 4 KiB/条（1024 × float32），sparse 按 `Σ(len(key UTF-8) + 64B)` 估算累计，总量不超过配置 `max_bytes`。不用条目数上限——sparse 条目大小跨数量级，条目数无法给出内存硬界。
- dense 以 float32 紧凑存储，命中时经与未命中路径相同的 `tolist()` 转换输出；sparse 存只读映射。保证命中与未命中响应逐位一致。
- 所有缓存读写仅在事件循环线程完成（查询在提交调度前、回填在推理结果返回后），无锁、无额外线程。命中不创建调度任务，不占用队列位置。
- 配置 `[cache] enabled` 与 `max_bytes`；`enabled=false` 时不查不填，行为与引入前一致。配置项总数 16 → 18。

## 替代方案

- Redis / SQLite 等外部或持久化缓存：单进程单 worker 服务无共享需求；持久层引入损坏、迁移与"服务不持久化用户文本"条款的冲突；违反最少代码。未采用。
- 文本级键（哈希原文）：可省去重复 tokenize，但键语义依赖字符串表示，需自行处理编码边界；tokenize 已在调度前发生、成本亚毫秒级，token 层键更精确对应模型实际输入。未采用。
- 条目数上限：实现更简单，但 sparse 条目从数百字节到 MB 级，相同条目数下内存占用差 3~4 个数量级，无法承诺上界。未采用。
- 推理线程（executor）内读写缓存：需要锁并扩大共享面；事件循环线程访问已覆盖全部需求。未采用。
- 不做缓存、仅靠微批优化：微批解决吞吐不解决重复计算，且两者正交；缓存实现量级远小于微批。缓存先行，微批按 [HANDOFF](../../HANDOFF.md) 原则等实际问题再立项。

## 后果

- 收益：重复文本延迟从推理级降到微秒级；全命中请求不占队列位置，缓解队头压力；命中计数进入现有日志，可观测命中率。
- 成本：常驻内存增加，硬上界为 `max_bytes`（估算口径）；配置项与测试面小幅增加；新模块约百余行。
- 风险：字节估算与真实 RSS 存在偏差，实施时以实测校准默认值；进程重启后缓存冷启动；长尾大条目可能挤占预算导致命中率下降（LRU 语义，接受）。
- 正确性前提：同一进程内 MLX 前向确定，命中与未命中逐位一致；该前提列入 SPEC-0003 验收场景实测。
- 后续影响：不改变对外契约；未来微批（PLAN 层 2）只需作用于未命中子批，与缓存正交。
