# ADR-0007：单 worker 批内合批

## 状态

已接受，2026-10-23。依据：用户明确指定“单 worker + 真合批”，要求在不增加 worker / 执行位的前提下优化批量入库；[SPEC-0001](../specs/0001-embedding-inference.md) 已增补批内合批契约。

## 上下文

当前服务为一进程、一个模型实例、一个推理线程、一个执行位和 FIFO 等待队列。原实现收到批量请求后逐条前向，每条都要重复一次模型调用和逐层同步；批量 16 条时，短文本的大部分时间花在固定开销上。

约束是 M4 / 16GB 上的内存可预测性、既有外部 API、输出顺序、`usage`、缓存和 429 语义。增加 worker 会引入独立的推理线程、MLX 全局默认流冲突、内存翻倍和更复杂的公平性问题；跨请求合批会改变队列与延迟语义。本决策只改变同一请求内的执行方式。

## 决策

- 同一请求内的未命中条目按 token 长度分桶；桶内右 padding 后一次前向。不做跨请求合批。
- 每个合批组 padding 后不超过 8192 tokens、最多 16 条、同组最长/最短不超过 1.25 倍；超预算条目单独执行。分组不对外暴露。
- attention mask 屏蔽 padding；CLS 仍取第 0 个 token；dense 仍为 float32 + L2；sparse 按原长度切片，语义不变。
- 执行位、worker、模型实例、FIFO 队列和外部 API 不变；不新增配置项，预算是代码常量。
- 任一组推理失败整请求返回 500 `inference_failed`，不返回部分结果。

## 替代方案

- **多 worker / 多执行位**：可提高并发，但 MLX 默认流是全局的，需要线程局部流、额外内存和公平性设计；与“单 worker”约束冲突。未采用。
- **跨请求动态合批**：需要改变队列语义、请求聚合和超时边界，可能让短请求等待长请求；本轮不采用。
- **保持逐条**：实现最简单，但短/中批的固定开销无法摊薄，也无法利用已验证的批内 padding。未采用。
- **不设预算的合批**：16×8192 会远超 2 GiB 内存指导值；实测 32768 padded tokens 峰值约 2 GiB，不适合 16GB 目标机。未采用。

## 后果

- 当前 M4 16GB 执行环境的独立进程实测：16×25 约 3.3x、16×256 约 1.18x、16×512 约 1.05x，16×1024 / 16×2048 / 4×8192 约 1.0x，混合长度约 0.97x；峰值最高 977.4 MiB。短/中批收益明显，1k 以上长块的 GPU 计算量不变。
- 1M token 按 1k 块入库仍约 5 分钟，合批不会带来数量级提升；256–512 块约 4.3–4.5 分钟。需要更大幅度提升时应减少 token 或更换模型/硬件，而不是继续增加 batch 或 worker。
- 混合长度有约 3% 回退（分组 padding 与小组合批开销），当前在 5% 容忍内；后续可按真实负载再评估小组合批/逐条回退启发式。
- 单 worker、单执行位、FIFO 和现有 API 保持不变；常驻服务尚未重启加载该版本，需另行授权。
