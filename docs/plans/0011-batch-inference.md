# PLAN-0011：单 worker 批内真合批

- 状态：已完成（2026-10-23；同一台 M4 实现与验证完成；同日已随最新版本部署上线，经用户确认）
- 关联：[ADR-0007](../adr/0007-batch-inference.md)、[SPEC-0001](../specs/0001-embedding-inference.md)、[PLAN-0003](0003-fused-attention.md)、[PLAN-0006](0006-performance-test.md)
- 来源：用户 2026-10-23 指定方向“单 worker + 真合批”，用于改善批量入库吞吐；不增加执行位、不改变外部 API。

设备说明（2026-10-26 用户澄清）：本文“本机”“当前 Mac mini M4”和“M4 目标机”指同一台 M4 16GB；独立进程基准与 launchd 服务验证是测量方式和部署阶段的区别。

## 目标与前置条件

在不改变 `/v1/embeddings` 字段、输出顺序、`usage`、错误码、缓存与 FIFO 队列语义的前提下，把同一请求内未命中的多条文本按长度分桶、右 padding 后一次前向，替代当前逐条 `for` 前向。执行位、worker、模型实例仍为 1；不做跨请求合批。

已确认的约束：

- 单条 ≤8192 tokens、单请求 ≤16 条 / 32768 tokens 不变。
- 每个合批组按 padding 后的 token 数不超过 8192；同组最长/最短长度不超过 1.25 倍；超出预算的条目单独执行。
- 右 padding，padding 不进入 `usage`；mask 必须屏蔽 padding；CLS 仍取第 0 个 token，dense 仍为 float32 + L2。
- 单条结果与合批结果在数值容差内一致；任一组失败整请求 500，不返回部分结果。
- 不新增配置项；预算以代码常量固定，后续有证据再决定是否配置化。

原型结论（当前 Mac mini M4 / 16GB、`batch=16`、合成定长文本；独立进程实测，不是线上服务）：合批对 25/256 tokens 有明显收益，对 512 约 1.05x，对 1k/2k/8k 基本无收益；原因是 1k 以上已由 GPU 计算而非每请求固定开销主导。详细数字见下方验证记录。

## 验证记录

### 基线（2026-10-23，当前 Mac mini M4 / 16GB）

`python -m pytest -q -m 'not real'`：99 passed，2 deselected。

`Embedder.embed` 逐条基线（16 条定长、`batch=16`、dense）：

| 场景 | 墙钟 | Metal 峰值 |
| --- | ---: | ---: |
| 16×25 | 0.901 s | 588.0 MiB |
| 16×256 | 1.326 s | 603.7 MiB |
| 16×512 | 2.346 s | 604.2 MiB |
| 16×1024 | 4.829 s | 631.2 MiB |
| 16×2048 | 10.916 s | 685.3 MiB |
| 4×8192 | 20.289 s | 1009.4 MiB |
| 混合（25–2048） | 3.904 s | 685.1 MiB |

### 原型合批（同环境）

| 场景 | 合批 | 相对逐条 | 峰值 |
| --- | ---: | ---: | ---: |
| 16×25 | 0.18 s | 约 5x | 596.8 MiB |
| 16×256 | 1.06 s | 约 1.2x | 777.3 MiB |
| 16×512 | 2.21 s | 约 1.05x | 977.4 MiB |
| 16×1024（2 组） | 4.79 s | 约 1.0x | 977.4 MiB |
| 16×2048（4 组） | 11.49 s | 约 1.0x | 977.4 MiB |
| 4×8192（4 组） | 20.89 s | 约 1.0x | 977.4 MiB |
| 混合（长度分桶） | 4.05 s | 约 0.97x | 777.4 MiB |

结论：真合批主要改善短/中批的每请求固定开销；1M token 若按 512–1024 切块，合批不会带来数量级提升。1M token 在 1k 块约 5.1 分钟，512 块约 4.5 分钟，256 块约 4.3 分钟（本机推算）。若目标是显著低于 5 分钟，应优先减少 token（摘要/跳过无关内容）或换更快的模型/硬件，而不是继续加并发。

### 实现后对照（2026-10-23，当前 Mac mini M4 / 16GB）

同一进程、先 warmup，再交替测逐条 `_forward` 与 `Embedder.embed` 各 3 次取中位数；输入为精确 token 长度的合成文本，`batch=16`，dense：

| 场景 | 逐条 | 合批 | 加速 | 峰值 |
| --- | ---: | ---: | ---: | ---: |
| 16×25 | 0.373 s | 0.113 s | 3.32x | 596.8 MiB |
| 16×256 | 1.250 s | 1.059 s | 1.18x | 777.3 MiB |
| 16×512 | 2.334 s | 2.230 s | 1.05x | 977.4 MiB |
| 16×1024 | 5.117 s | 5.046 s | 1.01x | 977.4 MiB |
| 16×2048 | 11.535 s | 11.565 s | 1.00x | 977.4 MiB |
| 4×8192 | 20.526 s | 20.492 s | 1.00x | 977.4 MiB |
| 混合（25–2048） | 3.881 s | 4.010 s | 0.97x | 842.5 MiB |

- 7 条真实长度样本（25、64、256、512、1024、25、128）合批与单条 dense 余弦均 ≥0.999999；sparse 键集合一致，权重在 `rel_tol=1e-4` 内。
- 16×1024 被分成 2 组 8 条，4×8192 被分成 4 组；均未超过 8192 padding token 预算。
- 混合长度出现约 3% 回退（分组内 padding 与小组合批开销），在 5% 容忍内；单条/合批结果仍一致。若后续真实负载以混合短文本为主，可再评估“仅当组内条数 ≥N 或 padding 浪费 <10% 才合批”的启发式。

**对 1M token 的含义**：按 16×256 合批约 258 秒（4.3 分钟），16×512 约 272 秒（4.5 分钟），16×1024 约 308 秒（5.1 分钟）；合批把 256 块推到与 512/1024 同级，但绝对下限仍由 GPU 计算决定。真实入库建议按检索粒度选 256–512 token/块，而不是为了合批强行切小到 25 token（向量数量从约 4 千增到 4 万，检索与存储成本上升）。

### 10 分钟连续入库（2026-10-23，当前 Mac mini M4 / 16GB）

按用户要求做 600 秒连续 dense 推理：`16×512`、8192 padded tokens/批；固定 512-token 合成输入循环，独立进程，不经过 HTTP、缓存、队列或去重。260 批、2,129,920 tokens、602.07 秒，平均 3,537.7 tok/s：

| 区间 | 批次 | tokens | tok/s | 批时 |
| --- | ---: | ---: | ---: | ---: |
| 0–30 秒 | 14 | 114,688 | 3,713.9 | 2.200 s |
| 30–63 秒 | 14 | 114,688 | 3,587.5 | 2.283 s |
| 63–95 秒 | 14 | 114,688 | 3,567.1 | 2.296 s |
| 95–125 秒 | 13 | 106,496 | 3,512.2 | 2.332 s |
| 125–600 秒 | 205 | 1,679,360 | 3,522.5 | 2.326 s |

稳定段（125–600 秒）线性斜率约 `-0.002 tok/s²`，基本无持续衰减；首 30 秒到稳定段约下降 5%，主要是预热/时钟稳定。峰值 977.4 MiB，进程 RSS 峰值 1,292 MiB，swap 前后均为 41.5 MiB used，`pmset` 未记录热警告或性能警告。该曲线只证明当前实现的持续 GPU 推理稳定性，不代表 HTTP、队列、真实语料或容量承诺；本机未重启服务。
