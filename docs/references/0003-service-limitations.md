# 当前服务的局限性

更新日期：2026-10-26。本文记录当前版本（同一台 Mac mini M4 16GB，dense + sparse 双路输出、FP16 + 批内合批 + 跨请求微合批）的能力边界，用于技术评估、接入决策与容量规划。

2026-10-23 已实施并部署 O1（请求日志观测）、O2（请求内去重）、O4（429 `Retry-After`），见 [SPEC-0004](../specs/0004-request-observability-and-dedup.md) / [PLAN-0010](../plans/0010-request-optimizations.md)；同一日实现单 worker 批内真合批，见 [SPEC-0001](../specs/0001-embedding-inference.md) / [PLAN-0011](../plans/0011-batch-inference.md)；FP16 attention 与跨请求微合批见 [PLAN-0012](../plans/0012-inference-optimizations.md) / [ADR-0008](../adr/0008-cross-request-micro-batching.md)。经用户确认，上述能力均已随 2026-10-23 的部署上线 M4 线上。下列条目已按当前版本更新。

本文是**快照与分析**，不是服务承诺，也不替代行为契约；与 [SPEC-0001](../specs/0001-embedding-inference.md)、[SPEC-0002](../specs/0002-dense-sparse-output.md)、[SPEC-0003](../specs/0003-result-cache.md) 冲突时以 Spec 为准。面向使用者的“适合 / 不负责”概览见 [README](../../README.md) 的适用场景与边界。

## 阅读方式

每条局限标注一种类型：

| 类型 | 含义 |
| --- | --- |
| **取舍** | 为换取单机可预测性、隐私边界或实现简单而有意放弃的能力；短期不计划改变 |
| **缺口** | 当前实现没有、接入后大概率会遇到的能力或防护 |
| **未验证** | 没有测试或观测证据，不能对外承诺；获得证据后应更新本文 |

事实依据为 Spec、代码与 Plan；推算值单独标注。本文不重复 PRD 的需求背景，也不把“未验证”写成“已失败”。

## 一、模型能力层

### L-01 固定 1024 维，不可降维【取舍】

接口只接受 `encoding_format=float`，不支持 `dimensions`，也没有 Matryoshka 截断或服务端降维（[SPEC-0001](../specs/0001-embedding-inference.md)）。稠密向量的存储与索引成本随条数线性增长，无法用“更小维度换更低成本”；要降本只能换模型或在调用方自行做降维，后者会损失语义且不在服务契约内。

### L-02 单条 8192 tokens 上限，拒绝而不是截断【取舍】

超限返回 400 `input_too_long`，tokenizer 不做静默截断（[SPEC-0001](../specs/0001-embedding-inference.md)）。长文档必须由调用方切分，切分边界与重叠策略直接影响召回；服务不提供切分建议，也不对切分后的语义完整性负责。单请求另有 32768 tokens 上限，因此最多容纳 4 条 8192-token 输入。

### L-03 只有 dense 与 token 级 sparse，没有 multi-vector 与 rerank【取舍】

BGE-M3 的多向量（ColBERT）表示、BM25 / SPLADE、第二模型以及服务端融合排序都不在范围内（[SPEC-0002](../specs/0002-dense-sparse-output.md)）。dense 与 sparse 的融合权重、召回后的重排都由调用方自行实现；服务不提供端到端检索质量保证。

### L-04 sparse 是原始词权重，且以 token id 为索引【取舍】

sparse 为 `ReLU(W·h + b)` 的逐位置权重，同一 token 取最大权重，排除特殊 token，不做 L2 归一化、长度归一化、IDF 或 top-k 截断（[SPEC-0002](../specs/0002-dense-sparse-output.md)）。索引是 token id 整数而不是词面，调用方需要自己维护词表映射；该表示与 tokenizer 绑定，不能跨模型复用，也不能直接当作 BM25 词频使用。

### L-05 8bit 模型与官方 fp16 不保证数值一致，且未做效果评测【未验证】

编码器是 8bit 快照，稀疏头由官方 fp16 检查点转换而来，二者精度不同源（[SPEC-0002](../specs/0002-dense-sparse-output.md) 的残余风险）。项目至今没有检索效果评测，README 明确不承诺召回提升；同一文本与官方全精度模型的余弦相似度、不同语料上的排序质量均无证据。接入前若对效果敏感，应自行做小规模对照，不要以“维度相同、接口相同”推断效果等价。

### L-06 单条向量对长文档是信息压缩【取舍】

每条输入只产出一个 1024 维向量，8192-token 文档的细节被压缩进同一向量；服务不提供分段向量或多向量检索。长文档中的局部事实、表格行或代码片段通常更难在单个向量中保留，典型缓解是调用方按语义切分后分别入库，或增加 rerank 阶段。

### L-07 不注入 query / passage 前缀，也未做领域适配【取舍 + 未验证】

服务原样编码请求文本，不自动添加 instruction、前缀或模板（[SPEC-0001](../specs/0001-embedding-inference.md)）；调用方若需要自定义前缀，只能自行拼进 `input`，这会改变 token 数与向量。模型对代码、表格、极短 query、否定句、专有名词等场景的效果没有在本项目中验证，也没有领域微调。

## 二、接口、服务与容量层

### L-08 单 worker 串行推理，批内合批 + 跨请求微合批【取舍】

一个进程、一个模型实例、一个推理线程；同一请求内未命中条目按长度分桶、右 padding 后合批前向，等待中的兼容请求按 15ms 窗口跨请求微合批（16 条 / 8192 token 上限，失败逐请求重试），不增加执行位（[SPEC-0001](../specs/0001-embedding-inference.md)、[inference.py](../../src/bge_embedding/inference.py)、[ADR-0008](../adr/0008-cross-request-micro-batching.md)）。合批主要摊薄每请求固定开销：当前 Mac mini M4 16GB 执行环境的独立进程观测 16×25 tokens 约 3.3x、16×256 约 1.18x、16×512 约 1.05x，16×1024 / 16×2048 / 4×8192 约 1.0x，混合长度约 0.97x；因此 1k 以上长块的吞吐仍由单条 GPU 计算决定，不会随 batch=16 线性改善。M4 同机 batch=1 观测 P50 约 25.1 / 273.9 / 2616 ms（25 / 945 / 5341 tokens，合成语料），冷路径约 4 QPS 量级。这些是观测值，不是 SLA 或容量承诺；合批的详细证据见 [PLAN-0011](../plans/0011-batch-inference.md) 与 [PLAN-0012](../plans/0012-inference-optimizations.md)。

### L-09 执行阶段没有硬超时，只有排队超时【缺口】

30 秒只约束“入队到开始执行”，已开始的推理不会被中断（[SPEC-0001](../specs/0001-embedding-inference.md)）。按 8192 tokens 约 4.8 秒观测线性推算，单请求最坏约 19 秒（4 × 8192，推算值，非实测）；只要前面排着两个这样的长请求，后来者的等待就会超过 30 秒并收到 429。服务没有执行上限、没有长请求隔离队列，也没有取消运行中计算的机制。

### L-10 队列满立即返回 429，无背压与优先级【缺口】

1 个执行位 + 19 个等待位，队列满时直接 429 `queue_full` 并附 `Retry-After: 1`（[scheduler.py](../../src/bge_embedding/scheduler.py)），不排队、不降级。没有按调用方、按长度或按请求类型的优先级；共享 Key 下任一调用方都能占满全部位置。重试、退避、批量拆分仍必须由调用方实现。

### L-11 客户端断开不取消已开始的 GPU 计算【取舍】

断开后任务继续算完、结果丢弃，执行位要到计算结束才释放（[SPEC-0001](../specs/0001-embedding-inference.md)）。这是为了避免强行中断 Metal 计算带来的不确定性，代价是超时重试或用户取消会放大无效算力消耗。

### L-12 健康检查是就绪状态，不是推理探针【缺口】

`GET /healthz` 只反映调度器是否已创建且未关闭（[app.py](../../src/bge_embedding/app.py)），不执行一次真实推理。Metal 或模型处于“进程存活但算不动”的状态时，探活仍可能返回 ready；进程崩溃才由 launchd 拉起。

### L-13 缓存只在进程内，且没有 TTL 与请求合并【取舍 + 缺口】

- 缓存随进程生命周期存在，重启即清空，不跨进程、不跨机器共享（[SPEC-0003](../specs/0003-result-cache.md)）。
- 没有 TTL、没有主动失效接口；键只含 token 序列与 `return_sparse` 标志，不含模型版本，正确性依赖“换模型必须重启”这一前提。
- 相同文本的并发首次请求不会合并：两个请求都在对方回填前查缓存，会各算一遍。
- 请求内重复文本已去重（2026-10-23），但跨请求的并发相同文本仍各自计算，不做 in-flight 合并。
- 容量按估算字节累计（dense 每条 4096 字节，sparse 另计），不是进程 RSS 承诺；超过 `max_bytes` 的单条不缓存。
- sparse 映射在进程内以引用形式传递，由序列化层只读使用；这是内部约定，未来若增加进程内直接消费方，修改返回值会污染后续命中。

命中请求绕过队列是收益，不构成局限；局限在于命中率完全取决于实际重复度，且服务不导出命中率指标，只能从日志聚合。

### L-14 单一共享 Key，无配额、限流与审计【缺口】

所有调用方共用一个 Bearer Key，没有多租户、按调用方配额、速率限制或审计归属；Key 轮换需要改配置并重启。日志不记录调用方身份，出现滥用或误用时无法定位来源。

### L-15 明文 HTTP，且没有 CORS【缺口】

服务只监听明文 HTTP，传输加密依赖 Tailscale / WireGuard 或前置反向代理；自身不提供 TLS 终止。应用没有挂载 CORS 中间件，浏览器跨域直连会在预检阶段失败，必须经同源反向代理访问。

### L-16 只兼容 OpenAI Embeddings 的子集【取舍】

不支持 `dimensions`、`user`、base64 输出、模型列表和 token-ID 输入；未知字段整单拒绝；`return_sparse` / `sparse` 是非标准扩展（[SPEC-0001](../specs/0001-embedding-inference.md)、[SPEC-0002](../specs/0002-dense-sparse-output.md)）。错误响应结构相近，但 `code` 取值是项目自定义的，客户端不应按 OpenAI 官方错误码分类做分支。接口只有固定的 `/v1` 路径，没有版本协商或废弃策略。

### L-17 可观测性只有轮转日志【缺口】

除 `/healthz` 外没有 metrics、tracing、告警或管理接口；日志只在请求完成时记录路径、状态码、耗时、批量、token、命中数以及 `wait_ms` / `exec_ms` / `ahead` / `dedup`。仍没有实时队列深度、P95 / P99 聚合、缓存命中率或异常率告警，这些只能事后从日志推算；`ahead` 是入队瞬间的前方任务数，不是当前队列水位。

## 三、部署、运维与验证边界

### L-18 单机单点，平台绑定 Apple Silicon + macOS【取舍】

一个进程、一台机器，没有高可用、副本、故障转移或水平扩展；多机部署需要各自维护模型、缓存与配置。运行时依赖 Metal 与 MLX，无法在 Linux / 容器中运行，也不能按通用 GPU 集群的方式扩容。

### L-19 用户级 launchd：依赖登录，重启有代价【取舍】

服务随用户登录启动，机器睡眠或未登录时不承诺可访问；没有系统级守护。重启会清空缓存并造成短暂不可用；停止时拒绝新请求并等待当前推理完成，没有跨请求的排空窗口。

### L-20 模型更新必须停机，且不支持多模型路由【取舍】

模型路径与 revision 在启动时固定，没有热加载、灰度切换或多模型共存；换模型等于重启进程并清空缓存。请求里的 `model` 只接受 `bge-m3`，不能按业务路由到不同模型。

### L-21 回滚与启动存在配置耦合【缺口】

旧版本遇到未知的 `[cache]` 段会拒绝启动，回滚代码时必须同步回退配置（[SPEC-0003](../specs/0003-result-cache.md)）。稀疏头是 dense 调用的启动前置，缺失时即使只调 dense 也拒绝启动（[README](../../README.md)）；模型目录不完整不是运行期可降级的错误。

### L-22 验证范围未覆盖故障、长稳与部分部署路径【未验证】

已完成的验证以基本冒烟、定向回归与性能观测为主；未做故障注入、30 秒排队超时实测、soak、整机重启或重新登录；同一台 M4 已完成部署与真实 HTTP 冒烟，当前版本证据见 [PLAN-0013](../plans/0013-milvus-sparse-format.md)。性能证据包括旧版同机 HTTP 单请求 / 并发、模型级批量与 10 分钟连续推理，以及优化后的进程内 ASGI / 回环 HTTP 测量；不能将不同版本与口径拼成当前版本统一基线，也不能外推到真实业务负载。因此当前不承诺容量、吞吐、可用性或恢复时间。详见 [HANDOFF](../../HANDOFF.md) 的当前验证范围与各 Plan。

## 影响排序与候选方向

下表按“接入后先撞上”的概率排序。候选方向只是评估建议，任何改变外部行为的动作都要先补 PRD / Spec，不在本文直接承诺。

| 优先级 | 局限 | 典型触发 | 候选方向 |
| --- | --- | --- | --- |
| 1 | L-09、L-10 长请求占用执行位 | 文档入库高峰、批量长文 | 增加执行超时或按长度分队列；调用方按 token 预算拆分并退避重试 |
| 2 | L-14、L-15 共享 Key 与接入方式 | 多团队、浏览器前端接入 | 前置网关做鉴权、配额、CORS 与 TLS；服务保持内网单 Key |
| 3 | L-17 缺少运行指标 | 排障、容量评估 | 导出队列深度 / 延迟 / 命中率指标，或固化日志分析脚本 |
| 4 | L-13 缓存边界 | 重复文本的并发入库 | 合并 in-flight 相同请求；按实际命中率决定是否值得做 |
| 5 | L-05、L-07 效果未验证 | 对召回质量有要求的业务 | 先做小规模检索对照或 rerank，再决定是否调整模型方案 |

## 维护方式

- 本文是 2026-10-22 的快照。Spec、实现或部署变化后同步更新对应条目，并在 [HANDOFF](../../HANDOFF.md) 记一行摘要。
- 新增条目先判定类型：有意设计的写“取舍”，实现缺失写“缺口”，没有证据的写“未验证”。获得证据后改写事实或删除，不把未验证项长期混在结论里。
- 本文不用于对外承诺 SLA、容量或检索效果；面向使用者的承诺口径以 Spec 与 README 为准。
